# Overall Plan — 무엇을 만들고 검증할 것인가

> 상태: 설계 초안 v0.1. [문서 홈](../README.md) · [구조](architecture.md) · [구현 계획](implementation-plan.md)

## 1. 대상 사용자와 업무

모의 금융 IT 운영 담당자가 실패한 대사 배치를 접수한다. Agent는 한국어 접수문과 내부 거래·외부 정산·작업 이력을 조사하여 재처리, 대기, 이관을 제안한다. 실제 송금·원본 금액 수정은 허용하지 않는다.

| 관측 조건 | 기대 업무 판단 |
|---|---|
| 자료 도착 미완료 | WAIT. 보이지 않는 미래 행을 추측하지 않는다. |
| 도착 완료 + ID·금액·상태 불일치 | ESCALATE. 원래 금액을 추측해 덮어쓰지 않는다. |
| 자료 완비·거래별 일치 + 배치 실패 | 유효한 승인 뒤 REPROCESS 가능. 입력 정산 자료가 없다는 이유만으로 재처리하지 않는다. |
| 기존 작업 반영 완료 | 결과 회수·검증. 성공한 같은 작업을 새 작업으로 다시 실행하지 않는다. |
| 반영 여부 불명 | 추가 조회로 상태를 구분. 상한 내 확인 불가면 이관한다. |

`REPROCESS`는 행동 제안이며 완료 증명이 아니다. WAIT와 ESCALATE도 정상 업무 결과다. 노드 실행 오류와 구분한다.

## 2. 범위

- 단일 Agent, 대사 업무 한 종류, 업무 Tool 6개, 원화 정수·거래 ID 1:1 비교.
- 로컬 SQLite·가상 시계·고정 시드 합성 데이터. GPU는 모델 추론에만 필요하다.
- 수수료·환전·분할 정산·실은행 접속·실제 개인정보·자율 코드 수정·모델 재학습 제외.
- 초기 업무 서비스는 동기 실행과 직렬화된 쓰기를 사용한다. 분산 worker·임의 네트워크 지연·운영 인증 플랫폼 전체는 후속 범위다.

## 3. 직접 구현할 기여

| 기여 | 제한된 최소 구현 | 핵심 반례 |
|---|---|---|
| 부정 증거의 선택적 재검증 | 존재·중복·배치 비교 3가지 조회의 영향 범위 | 빈 결과 뒤 관련 행 삽입 |
| 미확정 상태 구분 | 반영 여부×입력 변경 여부의 최대 4가설, 작업·입력 조회 | 같은 타임아웃, 서로 다른 실제 상태 |
| 시점별 판단 | 발생·수신·판단 시각, 지연·소급 정정·마감 이후 도착 | 나중에 온 자료로 과거 판단을 오답 처리 |
| 금융 반례 기반 완료 검사 | 금액 교환·대응 변경·잘못된 대상 근거·과거 승인 및 정상 ID 변환 | 합계는 같지만 거래별 금액 불일치 |
| 출처를 유지하는 보안·재개 | 외부 텍스트의 출처 유지, 승인 사칭·범위 이탈 차단 | 재개 문맥에 저장된 악성 메모 |

## 4. 현재와 목표 결과물

현재는 생성기·독립 파일 검사기·교육용 6사례·설명서가 있다. 목표는 이 자료를 실제 업무 DB에 적재하고, 승인·실행·중단·재개·결과 검사를 수행하는 실행 환경이다. 교육용 6개를 정식 개발셋이나 평가셋으로 이름만 바꿔 사용하지 않는다.

최종 산출물은 명세, 업무 서비스, R0/B0/B1/H 비교 실행, 통제된 QA와 독립 평가기, 원시 로그·집계 결과, 재현 노트북·대표 데모·실패 분석이다. 특정 성공률 향상을 사전에 약속하지 않는다.

## 5. 설계 질문

1. 전체 재검증의 정확성을 유지하며 관련 증거만 재조회할 수 있는가?
2. 추가 관측이 잘못된 확정과 불필요한 이관을 함께 줄이는가?
3. 당시 판단과 새 자료 도착 후 조치를 구분해 평가할 수 있는가?
4. 금융 반례가 검증기의 누락을 드러내며 정상 변환은 통과하는가?
5. 입력 출처·권한을 재개까지 유지하면 정상 업무를 보존하며 공격에 따른 잘못된 호출을 줄이는가?

비교군과 평가 원칙은 [평가 계획](../evaluation/experiment-plan.md), 결정 전제는 [결정 기록](decisions.md)을 따른다.
