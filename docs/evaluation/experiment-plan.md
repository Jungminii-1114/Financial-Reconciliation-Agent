# 비교 실험·동결·모델 교차 검토

> 제안 프로토콜. 현재 성능·비용 측정 결과는 없다. [Overall Plan](../overall-plan/README.md) · [지표](grading-and-metrics.md)

## 1. 공통 업무 서비스와 비교 설정

| 설정 | 구성 | 질문 |
|---|---|---|
| R0 | 고정 업무 규칙 + 공통 API | LLM 없이 해결되는 범위는 어디까지인가? |
| B0 | 업무 지침 + 기본 도구 루프 | 기본 Agent는 어디서 실패하는가? |
| B1 | B0 + 지속 상태·체크포인트·제한 재시도 | 상태 저장만으로 충분한가? |
| H | B1 + 관측 기반 상태 조정·증거 의존성·시점별 판단·완료 검증 | 추가 하네스의 기여는 무엇인가? |

6개 Tool·원천 입력·승인 정책·정보 권한·업무 API 보호를 동일하게 제공한다. H에만 operation refs를 보여주거나 B0에만 멱등성·승인 검사를 제거하지 않는다.

R0가 이 모의 규칙으로 대부분을 정확하게 처리할 수 있다면 그 결과를 그대로 보고한다. LLM의 이점을 만들기 위해 기준선 정보를 숨기거나 불필요한 자연어 복잡성을 추가하지 않는다. 이 프로젝트의 주요 검증 대상은 실행 신뢰성과 통제의 효과다.

## 2. 고정 조건

- 모델 ID·가중치/양자화·tokenizer·도구 템플릿·프롬프트·파서·decoding.
- 서버·하네스·평가기·DB schema·생성기·정답 명세의 버전/hash.
- case family·초기 DB·가상 시각·입력 이벤트·승인·장애 경계·공격 surface.
- 전체 Tool·조사·재시도·토큰·시간 상한. 재개 후에도 누적.
- trial마다 DB 격리, 같은 trial의 복구만 동일 DB 유지.
- 같은 trial에서 WAIT 후 새 자료로 시작하는 후속 검토도 동일 DB·budget_group_id로 총 비용을 합산한다. 후속 logical_run 생성으로 예산을 초기화하지 않는다.

모델 출력은 seed만으로 항상 결정적이라고 가정하지 않는다. 같은 초기 조건의 반복과 원시 응답을 보존한다. 제안된 예산은 [결정 기록](../overall-plan/decisions.md)에서 파일럿 후 확정한다.

## 3. 평가 규모 제안

| 평가 | 구성 | 실행 수 |
|---|---|---|
| 핵심 | held-out 12사건 × 기준/교란 2조건 × B0/B1/H × 3반복 | LLM 216 |
| 규칙 | 같은 12사건 × 2조건 | R0 24 |
| 보안 | held-out 정상/공격 20쌍 × 2조건 × H 보안 모듈 off/on × 3반복 | LLM 240 |

보안 개발용 20쌍을 별도로 제안한다. 20쌍의 정상/공격은 40조건이며 반복·모듈 비교를 늘렸다고 독립 QA가 늘어난 것은 아니다. 핵심 216+보안 240=456은 최종 비교용 LLM 실행 수 제안이며 파일럿·구성요소 제거·추가 모델은 별도 예산이다.

핵심/보안 사례가 같은 base family를 공유하면 중복·상관을 표시하고 독립 사례 총수를 단순 합산하지 않는다. 규모보다 시나리오·분모·실패 원인이 검증되는 실행을 먼저 완성한다.

## 4. 구성요소 제거 실험

개발셋에서 H의 관측 기반 복구, 선택적 재검증, as-of 근거, 완료 binding 검증을 각각 제외해 변화 원인을 본다. 기본 서버 보호는 유지한다.

보안에서는 의심 입력 표시·출처의 재개 보존·추가 하네스 게이트의 적용 범위를 기록한다. 모듈 off에서도 업무 서비스의 scope·승인·버전·멱등성 보호는 유지한다. 서버 때문에 실제 위반이 모두 0이면 이를 H 단독 효과로 주장하지 않고 호출 시도·비용·정상 업무 성공률을 비교한다.

## 5. 모델 교차 검토

### 개발 검토

한 모델이 작성한 시나리오·검사 코드를 다른 모델이 검토하게 할 수 있다. 모델명이 다른 것만으로 독립된 정답 검증은 아니다. 각 지적은 명세·실제 실행으로 확인하고 반영 여부·증거를 기록한다. 최종 정답 검토를 모델 다수결로 대체하지 않는다.

### 수행 모델 교차 실험

핵심 비교를 완성한 뒤 일부 사전 선택 사례에서 다른 모델에 동일 하네스·Tool·권한·예산을 적용한다. 모델명·버전·설정과 누락 사례를 기록한다. 모델을 바꾼 효과와 하네스를 바꾼 효과가 섞이지 않게 같은 모델 안에서 B1/H를 먼저 비교한다.

### Jev·LLM-as-a-Judge

설명의 근거 충분성·한계 명시 같은 좁은 의미 항목에만 선택적으로 사용한다. 사람이 검토한 한국어 사례에서 오류·일치도·비용을 먼저 확인하고, 별도 보조 지표로 보고한다. 산술·시간 순서·승인·권한·DB 효과는 모델이 판정하지 않는다. confidence를 실제 정확도로 취급하지 않는다.

runtime의 출력 정책은 evaluator의 비밀 canary·정답 labels를 받지 않는다. 평가 모델도 공격 원문에 의해 판정이 변할 수 있으므로, 모델 보조 점수가 결정적 안전 실패를 덮어쓰지 않게 한다.

## 6. 동결 체크리스트

- [ ] 모의 규칙·정답·상태 의미·기준선의 정보 권한 검토
- [ ] 정상 정답·고의 오류·정상 변환을 독립 평가기가 구분
- [ ] 실제 fault 발생 여부·commit/rollback·프로세스 재시작 확인
- [ ] 의미 계열·공격 template 단위의 development/held_out 중복 검사
- [ ] 모델·코드·데이터·예산·threshold·판정식 hash 고정
- [ ] 원시 아티팩트·재집계 경로·비용 상한 확인

동결 이후 수정은 결정 기록과 새 버전으로 남긴다. 최종 결과를 보고 프롬프트나 threshold를 조정했다면 같은 집합의 수치를 새로운 held-out 성능으로 발표하지 않는다.
