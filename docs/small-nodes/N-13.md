# N-13 · verify_business_outcome — 거래별 결과·실행 근거 검증

> **설계 초안 v0.1 / 미구현** · P1 · 소속 [B-05](../big-nodes/B-05.md). [Small Node 목록](README.md) · [공통 반환](common-result-contract.md)

## 1. 단일 책임과 실행 경계

실제 관측 가능한 원천·결과·작업·승인을 대조한다. evaluator의 expected.json이나 숨은 미래를 참조하지 않는다.

- LLM 사용: **사용하지 않음**.
- 업무 Tool: [TOOL-02](../tools/TOOL-02.md)·[TOOL-05](../tools/TOOL-05.md)와 같은 범위의 내부 read view.
- 이 문서의 내부 함수는 설계 함수다. 별도 Tiny Node나 별도 LLM 호출로 세지 않는다.
- 순서·조건부 엣지는 소속 Big Node가 관리한다. 이 노드는 다음 노드를 직접 실행하지 않는다.

## 2. 입력 계약

| 입력 | 타입·제약·출처 |
|---|---|
| `ExecutionObservation 또는 ActionProposal` | 검증할 완료·대기·이관 후보 |
| `case/batch, input_version, result_ref` | 대상과 입력 binding |
| `EvidenceBundle` | 거래별 자료·완결성·작업 근거 |

하네스는 ID·계약 버전·권한 binding을 검사한 상태를 전달한다. 모델이 작성한 ID나 상태를 검증 없이 신뢰하지 않는다.

## 3. 내부 처리 순서

1. 범위가 제한된 verification view에서 원천·결과·작업·승인 facts를 확보한다. 공개 Tool로 같은 업무 정보에 접근할 수 있어야 한다.
2. 거래 ID 대응·금액·통화·호환 상태·건수·중복·작업 대상·입력 버전을 코드로 검사한다.
3. 성공 효과에는 실행 당시 승인과 operation/result binding을 확인한다. 이미 적용된 승인 소비를 다시 요구하지 않는다.
4. WAIT는 당시 도착 미완료, ESCALATE는 불일치·미확정 근거를 검사한다.
5. 확인하지 못한 항목은 unknown으로 남기고 전체 완료를 통과시키지 않는다.

## 4. 구현할 내부 함수

| 함수 개념 | 책임 |
|---|---|
| `read_verification_view(refs, ctx)` | Tool과 같은 범위의 facts |
| `verify_transaction_links(view)` | 거래별·대상별 검사 |
| `verify_operation_binding(view)` | 승인·입력·효과 연결 |
| `build_verification_report(checks)` | 검사 결과와 근거 연결 |

업무 실행 노드는 `node(state: ReconciliationState, services: RuntimeServices) -> NodeResult[T]`를 기본 인터페이스로 한다. 평가 노드 N-16~19는 별도 `EvaluationContext`를 입력받으며 Agent State와 공유하지 않는다.

## 5. 출력 계약

공통 `status/data/diagnostics/outcome` 외피를 유지한다. 아래는 `data`의 최소 결과다.

| 결과 | 내용 |
|---|---|
| `VerificationReport` | check_id·expected_rule·observed_value·pass/fail/unknown·evidence_refs |
| `verification_digest` | 검증 대상·버전·결과 참조를 묶는 digest |

| outcome 후보 | 뜻 |
|---|---|
| `verified` | 필수 검사 통과 |
| `verification_failed` | 업무 조건 위반 |
| `verification_unknown` | 필수 관측 부족 |
| `evidence_changed` | 현재 입력과 불일치 |

`status=success`는 이 함수의 검사가 정상 종료됐다는 뜻이다. 대사 일치·쓰기 성공·최종 완료·공격 방어 성공은 각 업무 결과와 실제 상태로 판정한다. partial 허용 여부는 안전한 관측 보존에 한정하며 승인·쓰기·완료 허가를 partial로 통과시키지 않는다.

## 6. 오류·재시도·예산

| 오류·조건 | 처리 |
|---|---|
| `WRONG_RESULT_BINDING` | 다른 배치 성공 근거 거부 |
| `SNAPSHOT_INCOMPLETE` | 합계만으로 완료 금지 |
| `EVIDENCE_STALE` | 재조사 필요 |

재시도 여부는 상위 Big Node와 공통 누적 예산이 결정한다. Tool·모델 호출 전에 예산을 예약하고 실패·재개 비용도 남긴다. 저장·권한 오류를 성공으로 폴백하지 않는다.

## 7. 지속 상태·추적

검사항목·원천/결과 ref·버전·digest. runtime 검사 코드와 evaluator 구현은 분리한다.

node_id·logical_run_id·session_id·입출력 ref·상태·에러·실행 시간을 run_events에 연결한다. 저장 형식·복구 우선순위는 [지속 상태 계약](../contracts/persistence-and-recovery.md)을 따른다.

## 8. 최소 검증 사례

| 사례 | 확인할 결과 |
|---|---|
| 합계 유지 금액 교환 | 거래별 검사 실패 |
| 다른 배치 result_ref | binding 실패 |
| 정상 ID 일관 변환 | 통과 |
| 과거 승인으로 새 쓰기 | 승인 실패·과거 효과 조회는 허용 |
