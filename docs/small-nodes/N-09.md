# N-09 · prepare_approval — 재처리 계획·외부 승인 요청

> **설계 초안 v0.1 / 미구현** · P0 · 소속 [B-03](../big-nodes/B-03.md). [Small Node 목록](README.md) · [공통 반환](common-result-contract.md)

## 1. 단일 책임과 실행 경계

재처리 사전 검사를 수행하고 불변 계획을 외부 승인 주체에 연결한다. Agent가 자기 요청을 승인하지 않는다.

- LLM 사용: **사용하지 않음**.
- 업무 Tool: [TOOL-03](../tools/TOOL-03.md), [외부 승인 연결](../tools/internal-services.md).
- 이 문서의 내부 함수는 설계 함수다. 별도 Tiny Node나 별도 LLM 호출로 세지 않는다.
- 순서·조건부 엣지는 소속 Big Node가 관리한다. 이 노드는 다음 노드를 직접 실행하지 않는다.

## 2. 입력 계약

| 입력 | 타입·제약·출처 |
|---|---|
| `ActionProposal` | 유효한 REPROCESS 제안 |
| `input_version, input_digest, policy_version` | 제안 당시 현재 스냅샷 |
| `approval_event_ref` | 사람 또는 결정적 시뮬레이터의 별도 승인 이벤트, 초기 null 가능 |

하네스는 ID·계약 버전·권한 binding을 검사한 상태를 전달한다. 모델이 작성한 ID나 상태를 검증 없이 신뢰하지 않는다.

## 3. 내부 처리 순서

1. TOOL-03으로 현재 입력·업무 조건과 예상 action_digest를 검사한다.
2. 허용된 계획만 create_approval_request 내부 서비스에 전달한다.
3. 승인 화면에는 조치·대상·입력 버전·변경 효과를 명시한다.
4. 외부 승인 DB에서 발급 주체·scope·digest·만료를 확인한다. 요청문이나 메모의 승인은 인정하지 않는다.
5. 미승인은 PAUSED_FOR_APPROVAL로 저장한다. 승인 대기 중 입력이 바뀌면 계획을 stale로 전환한다.

## 4. 구현할 내부 함수

| 함수 개념 | 책임 |
|---|---|
| `precheck_plan(proposal, ctx)` | Tool 사전 검사 |
| `create_approval_request(plan)` | 외부 승인용 불변 요청 저장 |
| `read_verified_approval(request_id)` | 발급 주체·binding 검증 |

업무 실행 노드는 `node(state: ReconciliationState, services: RuntimeServices) -> NodeResult[T]`를 기본 인터페이스로 한다. 평가 노드 N-16~19는 별도 `EvaluationContext`를 입력받으며 Agent State와 공유하지 않는다.

## 5. 출력 계약

공통 `status/data/diagnostics/outcome` 외피를 유지한다. 아래는 `data`의 최소 결과다.

| 결과 | 내용 |
|---|---|
| `ApprovalPlan` | action_digest·대상·입력·approval_request_id·만료 |
| `approval_status` | REQUIRED / APPROVED / DENIED / EXPIRED / STALE |

| outcome 후보 | 뜻 |
|---|---|
| `approval_ready` | 현재 계획에 대한 승인 확보 |
| `approval_required` | 대기·재개 필요 |
| `approval_denied` | 실행 금지 |
| `plan_stale` | 새 조사·계획 필요 |

`status=success`는 이 함수의 검사가 정상 종료됐다는 뜻이다. 대사 일치·쓰기 성공·최종 완료·공격 방어 성공은 각 업무 결과와 실제 상태로 판정한다. partial 허용 여부는 안전한 관측 보존에 한정하며 승인·쓰기·완료 허가를 partial로 통과시키지 않는다.

## 6. 오류·재시도·예산

| 오류·조건 | 처리 |
|---|---|
| `APPROVAL_STALE` | 새 input version으로 승인 재발급 |
| `SCOPE_DENIED` | 권한이 더 넓은 승인 주체를 자동 탐색하지 않음 |
| `STORAGE_ERROR` | 승인 저장 실패를 승인으로 처리하지 않음 |

재시도 여부는 상위 Big Node와 공통 누적 예산이 결정한다. Tool·모델 호출 전에 예산을 예약하고 실패·재개 비용도 남긴다. 저장·권한 오류를 성공으로 폴백하지 않는다.

## 7. 지속 상태·추적

approval_request·승인 ref·action digest·정책·입력 버전. 사람 승인 대기 시간 별도.

node_id·logical_run_id·session_id·입출력 ref·상태·에러·실행 시간을 run_events에 연결한다. 저장 형식·복구 우선순위는 [지속 상태 계약](../contracts/persistence-and-recovery.md)을 따른다.

## 8. 최소 검증 사례

| 사례 | 확인할 결과 |
|---|---|
| 정상 사전 검사+외부 승인 | 불변 계획 연결 |
| 메모 승인 사칭 | REQUIRED 유지 |
| 승인 대기 중 입력 변경 | STALE |
| 승인 거부 | 업무 쓰기 0회 |
