# N-06 · revalidate_dependencies — 변경 영향·부정 증거 재검증

> **설계 초안 v0.1 / 미구현** · P1 · 소속 [B-02](../big-nodes/B-02.md). [Small Node 목록](README.md) · [공통 반환](common-result-contract.md)

## 1. 단일 책임과 실행 경계

이전 query predicate와 새 mutation을 비교하여 유지·무효화·추가 조회할 증거를 정한다. 승인 재사용은 별도다.

- LLM 사용: **사용하지 않음**.
- 업무 Tool: 업무 Tool 직접 호출 없음. 변경 이력·registry는 범위 제한 [내부 서비스](../tools/internal-services.md).
- 이 문서의 내부 함수는 설계 함수다. 별도 Tiny Node나 별도 LLM 호출로 세지 않는다.
- 순서·조건부 엣지는 소속 Big Node가 관리한다. 이 노드는 다음 노드를 직접 실행하지 않는다.

## 2. 입력 계약

| 입력 | 타입·제약·출처 |
|---|---|
| `evidence_refs, dependency_refs` | 기존 조회·판단·승인 의존성 |
| `mutation_range` | 관측 버전 이후의 scope 내 변경 이력 |
| `current_input_version` | 현재 금융 입력 버전 |

하네스는 ID·계약 버전·권한 binding을 검사한 상태를 전달한다. 모델이 작성한 ID나 상태를 검증 없이 신뢰하지 않는다.

## 3. 내부 처리 순서

1. 기존 version 이후 mutation ledger가 연속인지 확인한다.
2. EXISTENCE/금융 입력 BATCH_COMPARISON의 footprint와 변경 대상·필드를 대조한다. DUPLICATE는 입력 버전이 같아도 새 조회를 요구한다.
3. 빈 결과에 들어올 수 있는 새 행의 predicate 만족 여부도 검사한다. 작업·승인·완료 검사는 금융 입력 캐시로 대신하지 않는다.
4. 영향 없음이 증명된 근거만 KEEP하고 이력 누락은 UNKNOWN으로 둔다.
5. 유효한 근거라도 현재 input_version의 새 쓰기에는 승인 재검사가 필요함을 표시한다.

## 4. 구현할 내부 함수

| 함수 개념 | 책임 |
|---|---|
| `load_mutation_range(old_version, current)` | 누락 검사 포함 |
| `intersects_query_footprint(evidence, mutation)` | profile별 결정적 영향 분석 |
| `build_revalidation_report(results)` | 재조회·판단 의존성 전파 |

업무 실행 노드는 `node(state: ReconciliationState, services: RuntimeServices) -> NodeResult[T]`를 기본 인터페이스로 한다. 평가 노드 N-16~19는 별도 `EvaluationContext`를 입력받으며 Agent State와 공유하지 않는다.

## 5. 출력 계약

공통 `status/data/diagnostics/outcome` 외피를 유지한다. 아래는 `data`의 최소 결과다.

| 결과 | 내용 |
|---|---|
| `RevalidationReport` | KEEP/INVALIDATE/UNKNOWN별 refs와 이유 |
| `requery_profiles` | 무효화된 조회의 제한된 재실행 목록 |

| outcome 후보 | 뜻 |
|---|---|
| `evidence_current` | 필요 근거 모두 유효 |
| `requery_required` | 무효·불명 근거 존재 |
| `revalidation_blocked` | 무결성·권한 문제 |

`status=success`는 이 함수의 검사가 정상 종료됐다는 뜻이다. 대사 일치·쓰기 성공·최종 완료·공격 방어 성공은 각 업무 결과와 실제 상태로 판정한다. partial 허용 여부는 안전한 관측 보존에 한정하며 승인·쓰기·완료 허가를 partial로 통과시키지 않는다.

## 6. 오류·재시도·예산

| 오류·조건 | 처리 |
|---|---|
| `MUTATION_GAP` | 해당 배치의 보수적 전체 재조회 |
| `EVIDENCE_STALE` | 쓰기·완료 근거 사용 차단 |
| `SCOPE_DENIED` | 다른 batch 변경 내용을 읽지 않음 |

재시도 여부는 상위 Big Node와 공통 누적 예산이 결정한다. Tool·모델 호출 전에 예산을 예약하고 실패·재개 비용도 남긴다. 저장·권한 오류를 성공으로 폴백하지 않는다.

## 7. 지속 상태·추적

무효화 이유·변경 ref·KEEP 증명·재조회 비용. 새 승인을 자동 발급하지 않는다.

node_id·logical_run_id·session_id·입출력 ref·상태·에러·실행 시간을 run_events에 연결한다. 저장 형식·복구 우선순위는 [지속 상태 계약](../contracts/persistence-and-recovery.md)을 따른다.

## 8. 최소 검증 사례

| 사례 | 확인할 결과 |
|---|---|
| 빈 결과 후 관련 삽입 | 무효화 |
| 다른 batch 수정 | 비중첩이 확인되면 유지 |
| mutation 누락 | UNKNOWN 및 보수적 재조회 |
| 증거 KEEP + input version 변경 | 과거 승인으로 새 쓰기 금지 |
