# N-14 · finalize_case — 현재 조건부 종료 결정

> **설계 초안 v0.1 / 미구현** · P1 · 소속 [B-05](../big-nodes/B-05.md). [Small Node 목록](README.md) · [공통 반환](common-result-contract.md)

## 1. 단일 책임과 실행 경계

필수 검사와 현재 입력이 여전히 맞을 때 결정 시점·버전을 durable하게 기록한다. 입력이 달라졌으면 완료를 확정하지 않는다.

- LLM 사용: **사용하지 않음**.
- 업무 Tool: 모델 업무 Tool 아님. [완료 내부 서비스](../tools/internal-services.md).
- 이 문서의 내부 함수는 설계 함수다. 별도 Tiny Node나 별도 LLM 호출로 세지 않는다.
- 순서·조건부 엣지는 소속 Big Node가 관리한다. 이 노드는 다음 노드를 직접 실행하지 않는다.

## 2. 입력 계약

| 입력 | 타입·제약·출처 |
|---|---|
| `VerificationReport` | 필수 checks의 pass/fail/unknown |
| `expected_input_version, verification_digest` | 검증한 입력·결과 binding |
| `business outcome candidate` | REPROCESSED / WAITING_FOR_INPUT / ESCALATED / CANCELLED |

하네스는 ID·계약 버전·권한 binding을 검사한 상태를 전달한다. 모델이 작성한 ID나 상태를 검증 없이 신뢰하지 않는다.

## 3. 내부 처리 순서

1. 결과 유형별 필수 검사와 보고할 사실을 코드로 확인한다.
2. finalize_if_current 내부 서비스를 호출해 현재 version·result·case binding을 같은 직렬화 경계에서 재검사한다.
3. 조건이 맞으면 completion_decisions를 기록하고 decision_id를 회수한다.
4. 입력이 바뀌었으면 VERSION_CONFLICT로 반환하고 오래된 결정을 현재 완료로 기록하지 않는다.
5. 이후 입력 변경은 후속 사건으로 취급한다. 과거 as-of 결정을 소급 삭제하지 않는다.

## 4. 구현할 내부 함수

| 함수 개념 | 책임 |
|---|---|
| `validate_finalization_input(report)` | 필수 검사·사실 정합성 |
| `finalize_if_current(request, ctx)` | 서버의 조건부 검사·결정 저장 |
| `record_final_decision(decision)` | Agent 상태·결정 ref 연결 |

업무 실행 노드는 `node(state: ReconciliationState, services: RuntimeServices) -> NodeResult[T]`를 기본 인터페이스로 한다. 평가 노드 N-16~19는 별도 `EvaluationContext`를 입력받으며 Agent State와 공유하지 않는다.

## 5. 출력 계약

공통 `status/data/diagnostics/outcome` 외피를 유지한다. 아래는 `data`의 최소 결과다.

| 결과 | 내용 |
|---|---|
| `FinalDecision` | decision_id·outcome·decision_at·input_version·검증 refs·한계 |
| `finalization disposition` | FINALIZED / REVALIDATE / BLOCKED |

| outcome 후보 | 뜻 |
|---|---|
| `finalized` | as-of 결정 저장 |
| `revalidation_required` | 완료 직전 입력 변경 |
| `completion_blocked` | 필수 검사 실패·불명 |

`status=success`는 이 함수의 검사가 정상 종료됐다는 뜻이다. 대사 일치·쓰기 성공·최종 완료·공격 방어 성공은 각 업무 결과와 실제 상태로 판정한다. partial 허용 여부는 안전한 관측 보존에 한정하며 승인·쓰기·완료 허가를 partial로 통과시키지 않는다.

## 6. 오류·재시도·예산

| 오류·조건 | 처리 |
|---|---|
| `VERSION_CONFLICT` | 현재 입력 재조사 |
| `VERIFICATION_REQUIRED` | 근거 없는 완료 차단 |
| `STORAGE_ERROR` | 결정 ID를 지어내지 않음 |

재시도 여부는 상위 Big Node와 공통 누적 예산이 결정한다. Tool·모델 호출 전에 예산을 예약하고 실패·재개 비용도 남긴다. 저장·권한 오류를 성공으로 폴백하지 않는다.

## 7. 지속 상태·추적

decision_id·조건부 검증 facts·outcome·결정 시점·버전. 하네스 checkpoint와 업무 결정의 원자성은 가정하지 않는다.

node_id·logical_run_id·session_id·입출력 ref·상태·에러·실행 시간을 run_events에 연결한다. 저장 형식·복구 우선순위는 [지속 상태 계약](../contracts/persistence-and-recovery.md)을 따른다.

## 8. 최소 검증 사례

| 사례 | 확인할 결과 |
|---|---|
| 검증 직후 입력 변경 | 조건부 종료 실패 |
| 완료 저장 후 Agent 종료 | 동일 결정 재전달 |
| WAIT 판단 | 올바른 업무 결과로 저장 |
| 결과가 없는데 완료 요청 | 차단 이벤트 기록 |

이 단계의 custom marker 유무만으로 B0/B1을 실패 처리하지 않는다. 비교 평가는 실제 결과·금지 효과·보고 내용으로 독립 판정한다.
