# 독립 검증·테스트·한계

[사용 설명서](README.md) · [생성 방법](design.md) · [Feature](schemas.md)

## 1. 왜 생성기와 검사기를 나누는가?

생성한 정답을 다시 읽어서 “통과”라고 출력하면 같은 오류를 반복할 수 있다. 생성 쪽의 Python 집합/그룹 계산과 별개로 `validate.py`는 **자체 SQLite 상태·이벤트 해석·SQL 대조 계산**을 사용한다. `recipes.py`, `generator.py`를 import하지 않는다. 공유하는 것은 버전·설정 타입·직렬화 도우미다.

이는 구현을 분리한 검사다. 명세 자체의 오류·누락·산업적 타당성은 사람의 검토가 추가로 필요하다. 실제 DB 처리 결과를 채점하는 N-19 런타임 평가기는 아직 계획이다.

## 2. 검사 항목

| 범위 | 검사 |
|---|---|
| 파일 무결성 | manifest·설정·파일 해시·데이터 지문·누락/추가·심볼릭 링크·미허용 경로 |
| 데이터 스키마 | CSV 헤더·행 길이·정수 KRW·통화·상태·기본키·행 수 |
| 시간 | timezone·발생≤수신≤관측·이벤트 시간 증가·미래 행 비노출 |
| 입력 변경 | 이벤트 전/후 input_version +1, 동일 묶음 원자성, 정정 revision·필드 제한 |
| 업무 정답 | ID별 누락·알 수 없는 ID·중복·금액/상태 불일치·건수·합계 독립 SQL 계산 |
| 사건 성질 | 교환 시 합계 보존+오류 2건, 분할 도착 WAIT/WAIT/REPROCESS, 마감 이후 ESCALATE 등 |
| 복구 명세 | 반영 전/후 효과·승인 TTL·입력 변화·상태 조회 불가와 복구 의무의 일치 |
| 평가 분리 | split별 업무 recipe·보안 family, 쌍이 같은 split/group에 속하는지 |
| 대조 조건 | 반영 전/후 공개 입력 동일, 정상/공격 금융 입력·정답·사건 동일 |
| 정답 비노출 | 공개 자료에 정답 키·공격 라벨·어느 사례의 canary도 없는지 |
| 열람 파일 | HTML·SQLite·검증 보고서 각각의 별도 SHA-256 |

일반적인 프롬프트 인젝션을 식별하는 탐지 모델이 현재 검사기에 있는 것은 아니다. 공격 여부는 작성한 시나리오의 비공개 라벨이며 실제 탐지 결과와 구분한다.

## 3. 고의 오류 테스트

단순히 파일을 바꿔 hash가 달라졌다는 이유로 실패하는 테스트만 수행하지 않는다. 테스트에서는 고의로 값을 바꾼 뒤 **manifest의 hash와 지문도 다시 계산**하여, 아래 의미 오류가 여전히 거부되는지 확인한다.

- 잘못된 정답 행동·바뀐 거래 금액.
- 초기 관측에 미래 수신 행 삽입·timezone 없는 시각.
- 기본키 중복·입력 버전 건너뛰기·잘못된 revision·같은 시각의 이벤트 묶음.
- 반영 후인데 NOT_APPLIED라고 쓴 효과 정답·만료된 승인에 재승인 불필요라고 쓴 정답.
- 정상/공격 쌍 중 한쪽 금융 입력 변경·잘못된 공격 라벨·split 이동.
- 현재 또는 다른 사례의 canary가 공개 자료에 들어간 경우.

별도로 같은 seed 재현성·다른 seed 변화·시점 경계 포함 여부·소급 정정의 과거 보존·SQLite FK/무결성/비공개 정보 제외·출력 덮어쓰기 거부·case 경로 탈출 거부·HTML 외부 메모 escape·CLI 전체 흐름을 확인한다.

## 4. 실행 방법과 확인된 결과

```bash
python3.11 -m unittest discover -s tests -v
python3.11 scripts/dataset.py build --config configs/synthetic-pilot.json --out generated_data/pilot_v1
python3.11 scripts/dataset.py build --config configs/synthetic-benchmark.json --out generated_data/benchmark_candidate_v1
```

2026-11-05 로컬 Python 3.11.14에서 확인한 결과:

| 실행 | 결과 |
|---|---|
| 단위·통합·고의 오류 테스트 | 39개 통과 |
| pilot 기본 설정, 초기 내부 100행/사례 | 10사례, 보안 2쌍, 11시점 독립 검증 |
| benchmark 기본 설정, 초기 내부 100행/사례 | 98사례, 보안 40쌍, 107시점 독립 검증 |
| 두 프로필의 모델 호출 | 0회 |
| 실제 Agent·재처리·장애·방어 실행 | 미실행 |

위 39개는 합성기 검사의 수다. 현재 전체 테스트에는 [어댑터 검사](../data-adapter/validation.md)도 포함된다.

테스트 코드: [생성·시간](../../tests/test_generation.py), [의미 검증](../../tests/test_validation.py), [SQLite·HTML](../../tests/test_operator.py), [CLI](../../tests/test_cli.py). 작은 3행 사례로 여러 오류를 검사하고, 기본 100행 설정은 CLI로 별도 생성·검사한다. 수천만 건 규모 성능이나 Colab 환경의 실행을 검증한 것은 아니다.

생성물의 실제 hash·행 수·시점 수는 각 실행의 `manifest.json`과 `operator_view/validation_report.json`에서 확인한다. 코어 코드가 바뀌면 소스 hash가 바뀌므로 이 문서에 영구 지문을 고정하지 않는다.

## 5. 통과가 의미하는 범위

**확인한 것:** 이 모의 규칙 아래 파일·사건·정답이 서로 일치하고, 지정한 고의 오류를 별도 검사기가 거부한다.

**아직 확인하지 않은 것:** 은행 분포 대표성, 완전한 금융 업무 타당성, Agent의 성능, 실제 DB의 멱등 처리·승인, 장애 후 복구, 실제 인젝션 방어, 법규 전체 준수.

소스/파일 hash는 악의적인 동시 재작성의 진위를 증명하지 않는다. SQL 검사도 작성된 규칙 범위 밖 결함을 모두 찾는 것은 아니다. 후보를 보고 모델을 튜닝한 뒤 같은 자료를 독립 최종 평가라고 부르면 안 된다.

## 6. 다음 준비 사항

1. 개발 pilot의 거래·시각·정답 카드를 사람이 확인하고 모의 업무 규칙을 확정한다.
2. 이 버전의 [업무 DB 적재·재개·입력 사건 어댑터](../data-adapter/README.md)는 구현됐다. 다음으로 TOOL-01/02와 R0를 연결한다.
3. 현재 파일 검사기와 별도로 실제 operation/result/approval을 읽는 결과 평가기를 만든다.
4. 실제 반영 전/후 중단·새 세션 재개·권한/승인/버전/중복 보호를 시험한다.
5. 정상/공격 조건의 위반 시도·서버 차단·실제 효과·정상 업무 유지율을 분리 집계한다.
6. 그 후 최종 시나리오·조건·threshold·예산·정답 해시를 동결한다.
